模型名映射 把客户端请求里的模型名改指到别的上游模型（如 gpt-4o → geminiweb/gemini-pro）

客户端仍用别名调用（别名会出现在 /v1/models 里），网关在路由前把它解析成目标模型再转发。目标可写全限定名（provider/model）或裸模型名（回落到默认 provider）。
可写多行做「引流链」：第一行是主目标，后面每行是回退——主目标供应商无可用账号 / 额度耗尽 / 请求失败时，自动按顺序试下一行（例如把小浣熊放第一行烧快过期积分，runable 放第二行兜底）。别名不能等于目标；改完即热生效，落盘 data/model-mapping.json。
映射是硬规则：一旦配上就处处盖过「全局路由」的 prefer 顺序。不想让某条规则生效时用「停用」——配置留着、不再插手路由（该模型改按 prefer 顺序走），想恢复随时点「启用」；删掉则连配置一起没了。

网关密钥 按供应商收窄：决定每把客户端密钥能用哪些模型

            
            
          

          

            
            

              发给客户端的 /v1/* 与 /omni/v1/* 密钥。一把密钥可以授权多家供应商（这就是「多把 key 共用」反过来用：同一条 key 走多个渠道），也可以只勾一家做成专用 key。

              不勾任何供应商 = 全量（所有模型都能调）；勾选 = 收窄，该密钥只能调用这些供应商的模型，/v1/models 也会相应收窄，越权请求直接 403（不静默改道到别的供应商，也不会假装 404）。

              每张卡片下方会实时算出「这把 key 到底能调哪些模型」——请养成习惯：改了「全局路由」的优先级 / 默认供应商 / 模型映射之后，回到这里看一眼。上面出现过一次 api key is scoped to providers [raccoon, runable]; requested model routes to provider workbuddy 的 403，就是路由全改到 workbuddy、而这把 key 还锁着两家空壳渠道导致的。

              面板自己那把密钥恒为全量、不在本列表里（就是上面「服务」卡里的 API 密钥），所以在这里删光密钥也不会把面板锁死。改完点保存即热生效。

    积分快过期优先 raccoon / runable 的每日·每月积分会作废，优先烧快过期的
    
        
    
        
    
          
    raccoon 的「每日积分」当天清零、「每月会员积分」当月清零；runable 的日 / 月额度同理——不用就归零。开启后，网关会给窗口内仍有快过期积分的账号优先派单（先烧快过期的，再烧长期积分），并按「快照刷新间隔」后台刷新余额快照。
    
          
    
            
    启用
    
            
            
            
          
    
          
    余额快照只在选号时后台刷新（不阻塞请求，缺快照时退化为原有轮询）。上游只给钱包金额、不给逐笔到期时间戳，故到期时刻按「本地零点 / 下月 1 日」推导：窗口开大 → 命中账号变多、偏好被稀释。缺省启用。
    
        
    
      
    

      
    
        
    
          
    可靠性与限流 Gemini 失败兜底 + 入站按 IP 限流（默认都关闭）
    
        
    
        
    
          
    第三方兜底：当一次请求在 Gemini 侧失败或产出为空（无文本、无图）时，网关自动改用其它已配置的第三方模型重试同一请求，客户端始终只看到一个模型名。留空「候选模型」= 自动使用所有「看起来能聊天」的第三方模型（随机顺序）；填写则按顺序精确指定。
    
          
    
            
    启用第三方兜底
    
            
          
    
          
    
          
    按 IP 限流：对聊天类端点（OpenAI chat / Claude messages / Gemini generateContent）按客户端 IP 计数，超过「每窗口请求数」返回 429。
    
          
    
            
    启用按 IP 限流
    
            
            
          
    
          
          
    默认直接用 TCP 对端地址；仅当部署在会覆写 X-Forwarded-For 的反向代理之后才勾选。
    
        
    
      
    
      
    

      
      
    
      
    
        
    
          
    反检测指纹 Gemini Web 的 TLS / 请求头伪装，改完即时热生效
    
          
          
          
        
    
        
    
          
    直连上游时，网关会伪装成真实 Chrome 浏览器：TLS ClientHello 指纹（impersonate）、请求头顺序与取值、请求间隔抖动、Cookie 域名隔离。目标版本越高越像最新浏览器，但本构建的 TLS 指纹库最高支持到 chrome120——更高的目标会自动降级到最接近的可支持版本。经 HTTP/SOCKS 代理时 TLS 指纹不生效（回落到系统 TLS），其余伪装照常。
    
          
    
            
            
          
    
          
    
            
            
            
          
    
          
    
        
    
      
    
      
    

      
      
    
        
        
        
        
      
    
    
    

    
    
    
      
    
        
    
          
    出站代理 
    
        
    
        
    
          
    给面板上游（WorkBuddy）或某个供应商指定出站代理，未指定则直连。支持 http/https/socks5。单个代理直接填地址；代理池填列表 / 池 API，网关定期拉取探活、按请求轮询、失败自动切换。代理池可勾选严格模式：池里没有可用代理时直接失败、不回退直连——适合「该目标必须走代理才通」的场景（回退直连只会掩盖故障）。保存后热生效（无需重启），写入 config.json 的 outbound 段。
    
          
    
            
            
            
            
          
    

          
    
            
    
              添加代理
              
            
    
            
    
              
              
              
              
            
    
            
    或做成代理池（下面任一字段非空即按池处理，此时上面的「地址」忽略）：网关会定期拉取/探活、按请求轮询，连接失败自动切换下一个。
    · 池空时默认回退直连；勾选下面的严格模式则改为直接失败（不回退），适合必须走代理才通的目标。
    · 池里放你的 clash/mihomo 地址（如 http://newapi:17890）即可复用服务器上的分流规则。
